## Task 2: Security Audit

Full route-by-route pass over `backend/server.py` (4314 lines; unchanged since 2026-07-26's
avatar-rate-limit merge). Auth coverage on all handlers still matches the established
intentionally-public set; CORS still an explicit allowlist; no hardcoded secrets; existing
input-validation patterns (`re.escape`d regex search, TTS `voice_id` regex, `is_content_flagged`)
all still in place.

**Fixed — 4 mutating endpoints had no rate limit, unlike every sibling creation/guess endpoint:**
- `POST /gyms/join-by-code` — looks up an 8-hex-char (32-bit) invite code supplied directly by the
  caller with zero throttling. Every other secret-guessing endpoint in this file (`login`,
  `register`) is rate-limited specifically to prevent brute-forcing; this one lets an authenticated
  user script unlimited guesses to enumerate valid gym invite codes and join gyms they weren't
  invited to. Added `_rate_limited(f"gym_join_code:{user_id}", 10, 60)`.
- `POST /streams` (`create_stream`) — calls the real Livepeer API to provision a stream on every
  call, with no cap. An authenticated account could hammer this to run up Livepeer API costs/quota.
  Added `_rate_limited(f"stream_create:{user_id}", 10, 60)`.
- `POST /streams/{stream_id}/clip` (`create_clip`) — same shape: an uncapped call to the Livepeer
  clip API, gated only by stream ownership, not rate limited. Added
  `_rate_limited(f"clip_create:{user_id}", 10, 60)`.
- `POST /competitions` (`create_competition`) — unbounded `db.competitions` doc creation, the same
  growth-vector shape as `/posts`, `/emotes/generate`, and `/reports` (all already rate-limited).
  Added `_rate_limited(f"competitions:{user_id}", 10, 60)`.

All four follow the file's existing `_rate_limited(key, 10, 60)` convention exactly (same shape as
`posts:`/`emote_generate:`/`report:`).

**Checked, not touched:** `POST /streams/go-live` reuses an existing idle stream from the last 24h
before touching Livepeer, so it's already self-limiting on external-API cost — no separate rate
limit needed. `POST /posts/{post_id}/share` has no new-doc creation (just an `$inc` + a
fire-and-forget push notification) — a lower-severity notification-spam/harassment vector than the
four fixed above, flagging here rather than fixing since it needs a product decision (e.g. dedupe
per sharer+post) rather than a drop-in rate limit. `POST /streams/{stream_id}/whip` proxies to a
hardcoded Livepeer URL (not user-controlled, so no SSRF risk) and is already ownership-checked;
left alone since a legitimate broadcaster's own WHIP renegotiation traffic could plausibly need
more than 10 calls/min and there's no external growth vector (one stream, one owner).
