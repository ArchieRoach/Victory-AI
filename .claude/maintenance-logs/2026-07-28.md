## Task 2: Security Audit

Full route-by-route pass over `backend/server.py` (4324 lines). Auth coverage on all handlers

reference data, `/health`, `/waitlist/signup`, `/ads/*`, `/onboarding/social-proof`,

**Fixed — `POST /streams/schedule` had no rate limit:**
`create_scheduled_stream` validates the scheduled time and runs content through
`is_content_flagged`, but does an unbounded `db.scheduled_streams.insert_one` per call with zero
throttling — the same growth-vector shape as `/competitions` (fixed 2026-07-27), `/posts`,
`/emotes/generate`, and `/reports` (all already rate-limited). Added
`_rate_limited(f"stream_schedule:{user_id}", 10, 60)`, matching the existing convention exactly.

**Checked, not touched — `POST /follows/{target_id}`:** creates a doc and fires `_send_push` to
the target on every new follow, with no rate limit. This is the same fire-and-forget-notification
shape as `POST /posts/{post_id}/share` (flagged but deliberately not fixed on 2026-07-27, pending a
product decision on dedup rather than a blanket rate limit) — a user could follow/unfollow/refollow
distinct users to spam pushes, but the "Already following" guard blocks repeat-spamming the *same*
target, and fixing this properly needs the same kind of dedup logic as `/share`, not a drop-in
`_rate_limited` call. Leaving alongside `/share` for a human product decision rather than
papering over it with an arbitrary rate limit. `POST /gyms` (create) and `POST
/emotes/{emote_id}/purchase` were also checked: both are naturally self-limiting (Pro-subscription
gate + one-gym-at-a-time for the former, token-balance cost + one-time-unlock guard for the
latter), no fix needed. `POST /competitions/{comp_id}/vote` is one-vote-per-user-per-competition
(already guarded), no rate limit needed.

`python3 -m py_compile backend/server.py` passes.
